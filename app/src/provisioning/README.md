# 配网门户客户端

跟 `src/api` 是两套东西，不共用 `ApiError`：门户不是那个服务端，没有 token、
没有 401、没有 JSON 错误体，**而且它会在成功之后消失**。

协议来自 `main/provision.c`，记在 `docs/API-cloud-print.md` 5.0b。

## 三个非显然的地方

**一、成功之后门户就没了。** 固件验证通过后 `st` 变 1，3 秒后 `esp_restart()`，
热点随之消失。如果轮询正好错过那 3 秒窗口（App 被切到后台、手机慢了一拍），
我们看到的只有「门户不见了」——那既可能是配网成功，也可能是设备掉电。

`waitForConnectResult` 为此有一个 `lost` 结果。**它不猜。** 猜成功会让用户以为
配好了然后发现打不了印；猜失败会让他把一台已经配好的设备重配一遍。唯一的
权威答案是回到自己的 Wi-Fi 去 `GET /api/devices` 看那台 dev 在不在。

「连上过门户又失联」和「一次都没连上」也要分开：后者说明手机压根没在配网热点上，
下一步是去连热点，不是去看设备列表。

**二、超时和连不上要分开。** SoftAP 没有互联网，请求路由错了（走了蜂窝）会一直
挂着，那是超时；没连上热点是连不上。给用户的下一步不一样，所以每个请求都带
`AbortController`。

**三、老固件不返回 `dev`。** `readDeviceId` 此时抛 `malformed` 而不是编一个出来。
编出来的后果是 enroll 到一台不存在的设备上，密钥写进去也连不上，而用户完全
看不出问题在哪。见 API 文档 5.0b 的缺口。

## 用设备扫到的 Wi-Fi，不是手机扫到的

`scanNetworks` 读的是 `GET /scan`，那是**设备**扫出来的。设备的天线和位置跟手机
不同，手机能看到的 AP 设备未必够得着——用手机的列表会让用户选一个设备连不上的
网络，然后得到一个没法解释的失败。

## 测试

`mock-server/portal.mjs` 是按固件行为写的假门户，作为子进程起来打真 HTTP。
不打桩 `fetch`：这里要验的恰恰是「设备重启之后 fetch 会怎样」，打桩就等于
自己规定了答案。

它复刻了三个真实行为：重启后热点消失、`st` 的 3 秒窗口、老固件没有 `dev`。
`--reboot-ms=0` 就能造出「错过窗口」的场景。

`/__probe` 是只给测试用的端点，真固件没有。
