# URF 格式的核对状态

编码器写出去的每个字段，这里记它的依据和核对状态。
**没核对过的不要在别处声称已验证。**

核对基准是 `tests/fixtures/apple-gray8-2480x3507-300dpi.urf`——Apple 自己的光栅器
产出的真实 URF。取样方法见 `tests/fixtures/README.md`（一次性，手机上不需要 CUPS）。

## 页头字段

| 字段 | 偏移 | 当前取值 | 样本里的值 | 状态 |
|---|---|---|---|---|
| bits per pixel | 0 | 8 | 8 | **已核对** |
| colorspace | 1 | 0 | 0 | **已核对** |
| duplex | 2 | 1 | 1 | **已核对**（0 不是合法值，先前填的 0 是错的） |
| quality | 3 | 0 | 0 | **已核对** |
| 保留 | 4–11 | 全 0 | 全 0 | **已核对** |
| 宽 | 12–15 | 大端 uint32 | 2480 | **已核对** |
| 高 | 16–19 | 大端 uint32 | 3507 | **已核对** |
| dpi | 20–23 | 大端 uint32 | 300 | **已核对** |
| 保留 | 24–31 | 全 0 | 全 0 | **已核对** |

## 行结构

```
[1 字节重复计数 N] [RLE 包...]      ← 像素数攒够页宽即结束，没有终止字节
                                     该行共出现 N+1 次
```

| 包首字节 n | 含义 |
|---|---|
| `0 ≤ n ≤ 127` | 接 1 个像素，重复 `n+1` 次 |
| `n == 128` | **不是合法值**，样本里从不出现 |
| `129 ≤ n ≤ 255` | 接 `257-n` 个字面像素 |

两条已核对的结论，都推翻了先前的假设：

1. **没有 `0x80` 行结束符。** 先前按 `tools/reference/render.py` 的 `fix_page_count`
   推出的模型是错的。多写一个 `0x80` 会被解码成 129 个字面像素，
   整页从第一行起全烂——而这不会在任何环节报错，只会变成一沓废纸。
2. **行重复计数是必需的，不是可选优化。** 样本里 3507 行只用了 100 条记录、
   10470 字节；每行独立编码要 147KB。`Writer` 的 `line_repeat` 现在默认打开。

## 还没核对的

`dpi` 只在 300 上核过（PPD 没有 600dpi 选项）。字段位置和字节序确定，
取值 600 时没有理由不同，但没有实测样本。

真机打印仍未做——本表证明的是「编码器产出的字节与 Apple 光栅器一致」，
不是「这台打印机能正确打印」。后者要等 ESP32 桥和打印机接上。
