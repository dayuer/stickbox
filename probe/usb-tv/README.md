# 虚拟 U 盘探针

把 ESP32-S3-USB-OTG 插进电视的 USB 口，伪装成一支 U 盘，用来回答三个问题：

1. **电视认不认一支合成出来的 FAT32 U 盘？**
2. **盘上内容变了，怎样才能让电视重新扫描？** 这是整个「USB 信息屏」想法的命门。
3. **电视到底按什么顺序读了哪些扇区？**

跑完这三个实验，就知道那个产品想法成不成立。**在这之前不要写任何产品代码。**

> 本文是**操作手册**。设计决策、已验证的事实清单、结果判读和踩过的坑在
> [`docs/HANDOFF-usb-tv-probe.md`](../../docs/HANDOFF-usb-tv-probe.md)。
> 接手这个工程先读那份。

---

## 它是什么

一支 64 MiB 的只读 U 盘，但盘上的字节**不存在任何地方**——主机读哪个扇区，固件
现场算一个出来。这是必须的：这块板子没有 PSRAM，空闲堆只有 72~120 KB，装不下任何
真实大小的 FAT 卷；而一张 64 MiB 的盘里 99.9% 的扇区是零，不需要存。

盘上内容：

```
/SLIDE.JPG              ← 三张预置图之一
/DCIM/SLIDE.JPG         ← 同一份数据的第二条簇链
```

放两份是因为不确定电视的照片浏览器扫根目录还是扫 `DCIM`。两边都放，
哪边被读到会直接反映在 `/trace` 里。两条链各自独立（不共享簇），文件系统完全合法。

三张图的字节数刻意差很多（18 KB / 367 KB / 291 KB）。**这是实验的前提**：文件长度一变，
FAT 链长和目录项里的 size 字段就都变了，于是「电视有没有重读 FAT」变得可观测。

磁盘带标准 MBR、分区从 LBA 2048 开始、类型 0x0C，长得和真 U 盘一样——
有些电视不认没有分区表的「超级软盘」布局。

## 编译前必做：核对三处 API

容器里没有 ESP-IDF，**这份代码从未编译过**。`usbdev.c` 里有三处 API 我无法验证，
已逐个标 `[待验证]`。先核对再烧：

```sh
source ~/esp/esp-idf-v5.5/export.sh
idf.py set-target esp32s3
idf.py menuconfig          # 填「虚拟 U 盘探针」里的 Wi-Fi 凭据
idf.py reconfigure
./tools/check-api.sh       # ← 全部 ✓ 才继续
idf.py build
```

三处分别是：

| 位置 | 不确定的东西 | 错了怎么改 |
|---|---|---|
| `usbdev_start()` | `usb_phy_config_t` 的字段名、`usb_new_phy()` | 照 `check-api.sh` 打出来的真实结构体改 |
| `usbdev_replug()` | `tud_disconnect()` / `tud_connect()` | 没有的话删掉实验 C，只做 A/B |
| `tud_msc_*_cb` 里 | `tud_msc_set_sense()` 的参数顺序、`SCSI_SENSE_*` 常量名 | ASC/ASCQ 我已经用字面量了，只剩 sense key 枚举名 |

还有一个链接期的坑：**绝对不能让 `espressif/esp_tinyusb` 进到依赖里**。它的
`device/esp_tinyusb/tinyusb_msc.c` 无条件定义了全部 8 个 `tud_msc_*` 回调（强符号、
没有 `weak`、没有任何 Kconfig 逃生口），而它的 `tusb_config.h` 里
`#define CFG_TUD_MSC CONFIG_TINYUSB_MSC_ENABLED` —— 想开 MSC 类就必然把它的存储层
编进来，于是和我们的回调撞符号。它的存储层只支持 wear-levelling 分区 / SDMMC
（`esp_blockdev` 要 IDF 6.0.4+），落不到合成扇区上。所以本工程直接依赖底层
`espressif/tinyusb`，自带 `tusb_config.h`、描述符、PHY 初始化和 `tud_task()` 任务。

编过之后验一下符号只有一份：

```sh
nm build/usb_tv_probe.elf | grep tud_msc_read10_cb   # 应该只有一行
```

## 已经验证过的部分

虚拟磁盘的布局**不是没测过就交给你的**。`test/` 下有一套主机侧校验，不需要
ESP-IDF 也不需要板子：

```sh
./test/run.sh
```

它把 `main/vdisk.c` 原封不动编到 x86 上，导出镜像前 8300 个扇区，再交给
`test/validate.py` —— 一个**独立按 FAT32 规范写的**解析器（刻意不引用 `vdisk.c`
里的任何常量，否则就是把同一个错误验两遍）。

终局判据是：从簇链里把 `/SLIDE.JPG` 和 `/DCIM/SLIDE.JPG` 的字节抠出来，
和 `assets/slideN.jpg` **逐字节比对**。一致就说明 BPB 几何、FAT 链接、
目录项里的簇号、数据区落位全都对。

三张图各跑一遍，141 项检查全绿，包括：

- MBR 分区表、类型 0x0C、2048 对齐，另外三个表项为空
- BPB 的 15 个字段、`FilSysType`、扩展引导签名
- **簇数 126976 ≥ 65525** —— FAT32 的硬门槛，低于它主机会按 FAT16 解析然后失败
- 备份引导扇区与主引导扇区逐字节一致、FSInfo 三个签名
- FAT2 与 FAT1 完全一致
- `.` / `..` 项，以及 `..` 的簇号为 0（FAT32 里父为根时的规定）
- 大图的簇链跨越多个 FAT 扇区（717 簇跨 6 个扇区）仍然正确
- 两个副本的簇链完全不重叠

**没被验证的是 USB 那一层**（`usbdev.c`）—— 那需要真硬件。所以上面那张
`[待验证]` 表还是得过一遍。

## 接线

```
电视 USB 口 ──── 板子的 DEV 口      ← USB 数据 + 取电
电脑       ──── 板子的 Micro-USB 调试口  ← 串口日志（可选但强烈建议）
```

两个口同时插着，就能一边看电视界面一边看日志。控制台走 UART0，因为 OTG 外设
占用了 GPIO19/20，原生 USB-Serial/JTAG 用不了。

**安全要点**：固件把 `DEV_VBUS_EN` 和 `BOOST_EN` 都置 0，绝不往 DEV 口灌 5V。
VBUS 由电视提供，两个源对顶会出事。别改 `board_usb_device_mode()` 里那几行的值。

绿灯常亮 = 已被主机挂载；慢闪 = 没挂载。

联网后串口会打出控制面板地址：

```
★ 控制面板： http://192.168.x.x/
```

**用手机打开它**——你会站在电视前面，不是坐在电脑前。

## 实验

### 实验 0：电视认不认这支盘

插上，电视 → 信号源 → USB，看能不能列出 `SLIDE.JPG` 和 `DCIM` 文件夹，打开看看。

- **能看到图** → 问题 1 解决，继续。
- **认到盘但列不出文件** → FAT 布局问题。先看 `/trace`：如果 `bpb` 有读、`fat`/`dir` 没读，
  说明它拒绝了我们的 BPB。
- **完全不认** → 看 `/status` 的「挂载」和 `/trace`。如果一次读都没有，是枚举阶段就失败了，
  跟文件系统无关，去查串口日志里的 `tud_mount_cb`。

### 实验 1：怎样让它重新扫描 ← 最重要

协议是固定的三步，每种手段都走一遍：

1. 手机上点 **① 计数归零**
2. 点一种换片方式
3. 等几秒，看 `fat` 和 `dir` 的计数**有没有从 0 涨起来**

`fat`/`dir` 涨了 = 它真的重读了文件系统。只有 `data` 涨 = 它在用缓存的目录结构。

| | 手段 | 预期 |
|---|---|---|
| **A** | 热换（不弹出） | 大概率失败。但必须亲眼确认一次——万一成了，整个方案瞬间简单十倍 |
| **B** | 介质弹出 + UNIT ATTENTION | 最该成功的那个。`test_unit_ready` 先报 `NOT READY / 0x3A MEDIUM NOT PRESENT`，装回后报一次 `UNIT ATTENTION / 0x28`（「介质可能已更换」）——读卡器换卡就是这么干的，而且 USB 连接本身不断，对电视最温和 |
| **C** | USB 软拔插 | 最彻底。整条总线重新枚举 |
| **C+** | 软拔插 + 可变序列号 | 最后一招。很多主机按 `(VID,PID,序列号)` 缓存卷信息，序列号一变就等于一支全新的盘 |

**哪个最轻量且有效，就决定了产品形态。** 如果 B 行，这事很优雅；如果只有 C+ 行，
每次换内容都要重新枚举一次，电视界面会闪、可能跳回信号源列表，那「信息屏」
就只能是低频刷新的；如果连 C+ 都不行，方案退化成「只在开机时提供静态内容」——
那就得老实承认，换回 Wi-Fi 那条路。

### 实验 2：它到底读了什么

浏览器打开 `http://<ip>/trace`：

```
       0ms mbr  lba=0      x1
      12ms bpb  lba=2048   x1
      18ms fat  lba=2080   x8
      34ms dir  lba=4096   x1
      41ms dir  lba=4097   x1
      55ms data lba=4098   x36
```

能看出：读不读 MBR、认不认备份引导扇区、扫根目录还是 `DCIM`、
一次读几个扇区（吞吐上限）、有没有在空洞里乱读。

## 接口

动作全部是 `GET`，手机浏览器地址栏和 curl 都能直接打。

| | |
|---|---|
| `/` | 手机控制面板 |
| `/status` | 挂载状态、当前图、堆、分区域读计数 |
| `/trace` | 最近的读访问（按区域合并连续读） |
| `/reset` | 读计数归零 |
| `/arm?i=0\|1\|2` | 设定待生效的图（不改变主机看到的内容） |
| `/hot?i=N` | 实验 A：热换 |
| `/eject?ms=1500` | 实验 B：介质弹出周期 |
| `/replug?ms=1500` | 实验 C：USB 软拔插 |
| `/serial?vary=1` | 开可变序列号（下次软拔插生效） |

```sh
curl 192.168.1.50/reset
curl '192.168.1.50/arm?i=1'
curl '192.168.1.50/eject?ms=1500'
sleep 5 && curl 192.168.1.50/status
```

## 已知局限

- **吞吐**：ESP-FAQ 对 TinyUSB 的预期值是 6.4 Mbps。放照片够，放视频不够。
  `CFG_TUD_MSC_EP_BUFSIZE` 已设 4096（一次 8 个扇区）换吞吐，代价是 4 KB 常驻内存。
  没有 PSRAM，别再往上加。
- **单文件 1 MiB 上限**（`FILE_MAX_CLUS`）。够放照片。
- **图是预置的**，不是现场渲染的。现场生成 JPEG 要 `esp_new_jpeg`，而且得先确认它的
  API 能不能逐块喂——那是下一步的事，不是这个探针的事。
- **热换（实验 A）会让主机看到不一致的卷**，这是故意的。
- 读计数在 TinyUSB 任务里更新、在 HTTP 任务里读，没加锁。计数器竞争无害。

## 下一步取决于结果

- **B 或 C 有效** → 做内容通道：换成 `esp_new_jpeg` 现场渲染，Wi-Fi 拉数据。
  再加 HID 复合接口（MSC + HID 是一个配置两个接口，TinyUSB 原生支持）。
- **只有 C+ 有效** → 先量一次重新枚举对电视界面的干扰有多大，再决定刷新频率。
- **都无效** → 这条路到此为止。回到 Tizen WebSocket API（端口 8002）那条，
  USB 只留着当 HID 键盘用。
