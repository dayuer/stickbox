# StickBox 产品化：零售级开源硬件

> 方向（2026-10-17 定）：以**开源硬件**交付，但按**零售成品**的工程标准做。
> 保留零售的工程纪律，放弃零售的资金与法律负担。
>
> 任务拆解与状态见 [`PLAN.md`](PLAN.md) 的 T9 起。

## 1. 这条路线是什么

| 零售项 | 这里怎么办 |
|---|---|
| OTA 双槽 + 固件签名 + 回滚 | **保留**。社区设备刷不了新固件一样是死 |
| 崩溃回传 | **保留**。别人家里的板子，你拿不到串口 |
| 72h soak、电视兼容矩阵、电视背后 RF 实测 | **保留**。兼容矩阵公开成 `SUPPORTED-TVS.md`，这是用户买板子前唯一的决策依据 |
| 开机到出画面 < 15s | **保留**。电视关机会断 USB 供电，每次开电视都是一次冷启动 |
| Secure boot + flash 加密 | **放弃**，理由见第 3 节 |
| SRRC / CE / FCC | **不适用**，理由见第 2 节 |
| 注塑模具 | 换成开源外壳：STEP / STL，3D 打印或套现成 USB 外壳 |
| MOQ、库存、物流、退货、客服 | 全不要。issue 区就是客服 |

## 2. 一条不能越的线

**不要卖组装好的成品。** 卖 PCB 裸板、卖料、开源设计文件都没问题；一旦开始出售组装好的
无线电设备——哪怕按成本价、哪怕只有 20 台——多数法域的型号核准义务就落到出售方头上
（中国 SRRC、欧盟 RED、美国 FCC）。

用户自己买模组、自己打板、自己组装，这些义务不成立。WROOM-1 模组自带 FCC / CE / SRRC
**模组级**认证，意味着设备里那颗无线电本身是合规的——这是对社区问「这样做合法吗」的答案。

> 若将来真要卖成品，先回头读 `git log` 里这一节，重新做认证预算（量级 $8k–15k，需实际询价）。

## 3. 放弃 secure boot，保留 OTA 签名

这两件事常被混为一谈，其实无关：

**Secure boot（放弃）** 把设备锁死在签名固件上，等于收回用户刷自己固件的权利，与开源硬件的
前提直接冲突。威胁模型也撑不住：设备里唯一的资产是一机一把的设备密钥（NVS `cloud/devkey`，
由服务端 `/api/device/register` 签发），泄露的后果是「拿到物理设备的人能看到这台设备本来就在
电视上用 250px 大字显示的数据」。为这个代价关掉用户的刷机权，不划算。

flash 加密同理，一并不开。

**OTA 固件签名（保留）** 防的是另一件事：服务端被攻破后批量下发砖头固件。用
`CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT` —— 校验签名但不锁 bootloader，用户照样能用
串口刷任意固件，OTA 通道只接受私钥签过的。公钥编进固件，私钥不入库。

## 4. 三个架构决定

### 4.1 服务器地址必须在 NVS，不能在编译期

现状（`rom/main/cloud_creds.h.example`）是编译期常量：

```c
#define MQTT_URI   "mqtts://mqtt.stickbox.ai:8883"
#define API_BASE   "https://mqtt.stickbox.ai/api"
```

后果：**发不出一个所有人都能用的预编译 bin**。每个自托管的人都得装 ESP-IDF 自己编译，
「浏览器里一键烧录」这条最大的获客杠杆就没了。

改法：地址进 NVS，配网页加一个字段，默认填公共实例。见 T11。

### 4.2 不绑定官方服务器

开源硬件最被诟病的就是「厂商关服，设备变砖」。三条底线：

- 服务器地址可改（4.1）
- `docker-compose up` 能跑起完整后端，公共实例只是方便，不是依赖
- 服务端不可用时电视上显示明确的离线状态，不是黑屏或花屏

做到了，项目的生命周期就不取决于维护者还有没有兴趣。

### 4.3 服务端渲染 + 数据源插件化

把 1080p 看板的渲染从固件挪到服务端，固件只负责取帧、缓存、推流。

理由：
- **贡献门槛**：加一个数据源 = 服务端写一个插件，不碰固件、不需要有板子、不需要装 IDF。
  这是把一个人的项目变成社区项目的唯一现实路径
- **抗依赖**：Claude 用量是第一个数据源，不是唯一的。`claude -p /usage` 是未公开的输出格式
  （坑见 PLAN T2），哪天变了，设备不该跟着变砖
- **工作量**：设计稿那套 270° 弧、三种字体、字距 −.02em，在 Go 里是一天的活；在 MCU 上是
  T4 整个任务
- **字体许可**：Barlow / Barlow Condensed / Noto Sans SC 是 OFL。放服务端就不涉及预渲染字模
  这种衍生品的署名与 Reserved Font Name 义务

代价与前提：
- 断网时没画面 → flash 里存一张「离线」兜底帧
- 每秒级动效没了（冒号闪烁）→ 帧每分钟换一次，一台设备约 20Kbps
- **需要 PSRAM**：整帧 JPEG 约 120KB，当前模组（MINI-1-N8，无 PSRAM）放不下。见 T12

> **2026-10-17 更正**：本节原先还列了第五条理由「板上内存放不下」，并据此搁置 T4。
> T8 完成后带 TLS 的历史最低是 **63.5KB**（原为 32KB），T4 多占 24KB 后约 39KB，余量够用。
> **内存不再是理由，板上渲染是可行的**。上面四条理由仍然成立，但这变成了一个需要权衡的
> 选择而不是唯一出路——决策见 `PLAN.md` 的 T13。

### 4.4 两种部署形态：自建，或租用公共实例

> **决策（2026-10-18，用户）**：用户自建服务端，或者租用维护者的服务端。

这是 §4.2 的延伸而不是新约束：**同一份固件、同一份服务端二进制，两种跑法**，
不允许出现「只有云端才有」的功能——一旦出现，自建就从一等公民退化成阉割版。

租用意味着要按量计费，而计费只在**数据面**有意义：控制面（配对、鉴权、
帧版本通知）流量极小，放哪都不心疼；真正的视频字节放错地方就是每台设备
每月上 TB。所以控制面与数据面必须在架构上分开，并按真实成本分档。

频道模型、三档配置、流量数量级、以及门槛性的未决问题见 **`CHANNEL.md`**。
那边第 4 节是省流量的总开关（按「字节会不会变」分四类），第 5 节记了
「单一流、无缝切换」这条硬需求和它的推论，第 10 节有一条必须先跑出结论的
实验——在它之前不要动架构。

## 5. 硬件

### 5.1 支持现成开发板，不只支持自家 PCB

固件要有一层板级引脚抽象，至少三个目标：

| 目标 | 说明 |
|---|---|
| 通用 ESP32-S3-WROOM-1 开发板 | 淘宝 / 立创约 ¥35，最容易买。双 Type-C（原生 USB-OTG + CH343P 串口）、WS2812、BOOT/RST |
| 官方 ESP32-S3-DevKitC-1 | 对照基准 |
| StickBox PCB | 自家 USB 棒形，见 5.3 |

**模组一律选 N16R8**：16MB flash + 8MB PSRAM。
- 8MB PSRAM 是 4.3 服务端渲染的前提
- 16MB flash 放得下 OTA 双槽（2×3M）+ 离线兜底帧 + 余量；8MB 够用但紧
- **N8R2 不要用**：2MB PSRAM 存不下 1080p 工作集

### 5.2 RF：电视背后是家里 Wi-Fi 最差的位置

设备被夹在电视金属背板和墙之间。自家 PCB 版用 **WROOM-1U + 外置天线**；开发板版是 PCB
天线，属最坏情况——实测结果写进文档让用户自己判断，并在包装/文档里建议用 15cm USB 延长线
把棒子挪到电视侧面。

必须在真实客厅测：墙那一侧、路由器在另一个房间。实验室测不出来。见 T14。

### 5.3 交付物

- **PCB**：KiCad 源 + Gerber + 带 LCSC 料号的 BOM，做成 JLCPCB 可直接下单贴片
  （用户约 $30 打 5 片装好的，维护者零库存）
- **外壳**：STEP + STL，外加「这些现成 USB 外壳装得下」的清单
- **供电**：电视 USB-A，5V。多数电视 USB 2.0 口只给 500mA，S3 发射峰值约 350mA，留足体电容。
  电视关机断电是常态——不加电池（加了要 UN38.3 运输认证），当冷启动处理，指标压在开机 15s 内出画面

## 6. 发布工程

- **浏览器烧录**：GitHub Pages 上一个 ESP Web Tools 页面，插 USB、点一下、WebSerial 直接刷，
  不装任何东西。这是获客的头号杠杆，优先级高于自家 PCB
- GitHub Release 附合并好的 factory bin + 签名
- semver + CHANGELOG；OTA manifest 由服务端提供
- 自托管：`docker-compose up` 起完整后端

## 附：下行指令确认（T18）的一处已知代价

设备连续 4 次没回 ACK 就会被标成「不回 ACK」，之后的下行只发一次、不跟踪。
这是为旧固件准备的——否则每条 usage 都投 4 次、每次刷一条 ERROR，真告警会
被淹掉。

代价是：**新固件如果偶然连丢 4 次 ACK（比如长时间弱网），会被误标一次，
之后有一条下行不被跟踪确认。** 设备下次回 ACK 时标记自动清除，恢复跟踪。
这个窗口可以接受——丢的是「确认」，不是指令本身，指令照常带 cid 发出去了。
