# 照片上电视：SD 卡本地轮播

状态：**规格基线（2026-10-18）。** 产品决定见 `DECISIONS.md` D8–D12；
SD 链路已实机验证（`experiments/sd-bare-sector-round1.md`）。本文同时是
服务端（P1）与固件（P2）的接口依据；与 `DECISIONS.md` 冲突时以决策为准。
本文不依赖 `play`（外部 TS 流）任务。

2026-10-18 集成方裁决（已写进正文）：
- SD 是**专用整卡、从扇区 0 开始**；没有合法超级块时设备只上报 `uninit`，
  **不写卡**。用户执行 `stickbox-agent photo init` 后，服务端生成一次性
  `init_token`（10 分钟有效）放进清单；设备只在这种卡上格式化，成功后把
  token 前 8 位放进 `status.photo.init_done`，服务端立即清除授权。卡级损坏
  绝不自动格式化；只有 `photo init --force` 生成的 token 才允许格式化
  「魔数存在但 CRC 都坏」的卡。
- 读缓冲 **4KB**；下载与读卡互斥，取帧排在下照片之前，按队列顺序而非并发。
- 设备**不存离线 JSON 清单**；64B 索引项带 `duration_s` 和 `order`，断网照常播。
- 照片留白用**纯黑 #000000**；支持 JPEG/PNG，HEIC 服务端 415。
- 服务端返回**完整清单**，设备按自身能力过滤；`plv` 全局有效，不认识的
  `kind` 整条忽略。
- 硬配额：每人 200 张、64MiB；超了拒绝（409），不 LRU 淘汰用户照片。

## 已定决策（用户）

- **D3/D4** 流的起点在设备侧；流内无缝切换，不接受电视黑一下
- **D8** 照片存 SD 卡，**可选功能**：有 SD 槽的板子才有照片，其余板子只显示看板
- **D9** SD 用**裸扇区**，不用 FAT；按需挂载
- **D10** 照片**纯显示**，不叠时钟和用量卡片

## 0. 选型结论（原先的先决冲突，已关闭）

目标板（通用 WROOM-1 / DevKitC-1 / StickBox PCB）多数没有 microSD 槽，所以照片是
**带 SD 槽板子的可选功能**（D8）。后果写死在设计里：

- 无 SD 槽 / 没插卡 / 挂载失败：行为与现在完全一致，见第 8 节
- 服务端**不得**假设每台设备都有照片能力：设备在 `status` 里上报 `cap/ready`
  （第 5.4 节）；清单始终完整返回，**由设备按自身能力过滤**，无能力设备不会下载照片
- 是否给 StickBox PCB 加 SD 槽是**硬件另议**，不阻塞本设计

## 1. 为什么 SD 是对的原语（如果硬件给得起）

照片的字节**永不变**。流式的本质是「每次播放把同一批字节重发一遍」，
所以对照片用流式等于把同一批字节一遍遍过公网。缓存才是对的原语：
**传一次，播无限次**（`CHANNEL.md` 第 4 节）。

| | 每设备 |
|---|---|
| 200 张 1080p 照片（约 250KB/张） | **50MB 一次性** |
| 同样内容做成 24/7 轮播流 | 约 52GB/月，永远每月 |

**容量不是问题，一张 1GB 卡就够**。256GB 对照片过剩约 1000 倍——那个容量是给视频的。

---

## 2. 设备侧为什么是加法而不是改造

`rom/main/stream.c` 的发送循环已经是为「帧边界切换」设计的。它自己的注释：

> 每帧只在这一个临界区里看一次共享状态，拿到的东西全部快照进局部变量…
> 换帧包、换时钟带、从配对页切到真实看板，都只改共享状态，而共享状态
> 只在帧与帧的边界被读到。

已经有三种模式在帧边界切（帧包 / 时钟带页 / 配对页）。**SD 照片是第四种**，
照同一个模式加：在同一个临界区里多快照一个「当前照片」，往下不回头。

两个关键后果：

- **照片不进带缓冲。** 带缓冲只在有数字卡片要替换时才用。照片是一整张 JPEG，
  没有槽、没有拼接，`s_band` / `BAND_CAP` 一个字节都不碰
- **照片不建段表。** 不用 `fp_seg_t`，直接 `read(8KB) → send_all` 循环到 EOF。
  `s_fp_hold` / `fp_wait_idle` 那条 mmap 生命周期保护也完全不涉及

AVI 的 `00dc` 块头要先写帧长再写字节——照片长度从清单（或文件大小）拿，没问题。

## 3. 存储层：裸扇区（D9）

不用 FAT。理由：设备自己从服务端下载照片，**卡不需要被电脑读**，所以不付 FATFS 的
堆；掉电语义也可以自己定，照 flash 槽那套（魔数 + CRC，头部最后写）。

代价（产品上要接受，也要对用户说清楚）：
- **SD 卡是专用整卡，从扇区 0 开始**，卡上原有数据会被覆盖；不能插卡直接拷照片。
- **初始化用一次性 token**：用户执行 `stickbox-agent photo init`，服务端生成随机
  `init_token`（10 分钟有效）放进清单（`init_force` 表示是否允许 force）。
  设备仅在以下条件同时成立时格式化：
  - 两个超级块都**没有 `SBPH` 魔数**（空白/别的文件系统）；或 `init_force=true`
    且魔数存在但两个 CRC 都坏；
  - 清单里带着未过期、未使用的 token。
  格式化成功后把 token 前 8 位放进 `status.photo.init_done`，服务端据此立即清除授权；
  超时也清除。清单里没有 token 时**绝不格式化**。
- **卡级读失败（读不出/初始化超时）永不格式化**，只上报 `state=fault`，看板照常。
- 真实拔电可能让卡对板子不可用（实验已复现），恢复靠用户重新格式化；产品行为同上。

**堆**：sdmmc 驱动 + **4KB 读缓冲**（不是 512B，也不是 8–13KB）+ 按需读索引项。
**按需挂载**：清单里没有 `photo` 条目时不初始化 SD。**下载与读卡互斥**：联网取清单/
下载 → 写卡 → 卸载 → 本地读卡推流；取帧排在下照片之前，是队列顺序，不是并发。
实测数字见 `experiments/sd-bare-sector-round1.md`。

## 4. 卡上布局（裸扇区）

512B 扇区。照片是不可变素材，所以布局很简单，不需要通用文件系统。

```
扇区 0、1   超级块 A/B：魔数 "SBPH" + 版本 + 序号 + 索引区/数据区起点 + CRC32
            每次改写交替写 A/B，取序号最大且 CRC 合法的那份（掉电安全）
索引区      固定 256 项 × 64B：
            sha256(32) | size(4) | 起始扇区(4) | duration_s(u16) | order(u16) |
            状态(1) | 保留 | CRC32(4)
数据区      照片本体，按 4KB 对齐，连续存放
```

- **专用整卡**：从扇区 0 开始，不保留实验区、不识别 FAT；只有清单带未过期
  `init_token` 时才允许首次格式化（详见第 3 节）。
- **内容寻址**：以 sha256 为键。重复上传不占第二份；改顺序、改时长、改名一个字节都
  不用重传（那些是清单属性）；校验内生
- **项目上限 256**，总用量只占数据区一小段（200 张 ≈ 50MB），**其余容量不用**
- **写入顺序保证掉电安全**：先写数据 → 校验 sha256 → 最后才写索引项的 CRC 与状态为
  `valid`。索引项不完整（CRC 不符/状态非 valid）一律视为不存在
- **分配**：对 ≤256 个索引项按起始扇区排序后 first-fit，**不建位图**（千兆卡位图要 32KB）
- **回收**：清单里没有的 `valid` 项置为 `free`。**回收只在本方案的索引/数据区内，
  不触碰区外任何扇区**

**索引项自带 `duration_s` 和 `order`**：设备不保存离线 JSON 清单，断网时直接按索引
里的顺序和时长继续播；联网后拉到新清单再更新索引元数据（不重复下载字节）。

## 5. 播放清单协议

### 5.1 MQTT 只报版本，清单走 HTTPS

现状（T24 已上线）：`printer/{dev}/frame` 发 `{"ver":N,"pl":[{id,ver,secs}]}`。

**照片库不能走内联 `pl`**：200 张照片的元数据内联进 MQTT 是几十 KB 的消息，
而 MQTT 消息该保持很小。改成和帧包一样的两段式——**通知版本，设备去取**：

```json
{"ver": 12, "plv": 7}
```

- `ver` 保持原义（主主题帧包版本），**老固件只认它，行为不变**
- `plv` 是播放清单版本。设备发现 `plv` 变了 → `GET /api/device/playlist`
- 内联 `pl` 仍受 T24 修复的硬预算约束（最多 8 项、整条消息 ≤800 字节，老固件 MQTT
  缓冲只有 1024 字节，超出整条丢弃且之后不再更新）。`plv` 字段只增加几个字节，不得
  突破该预算；**清单文档是唯一权威**，内联 `pl` 只作兼容

### 5.2 清单文档

`GET /api/device/playlist`（设备令牌；带 `ETag: "<plv>"` / `If-None-Match`，命中 304）：

```json
{
  "plv": 7,
  "init_token": "3f2a9c01d4e5b6a7",
  "init_force": false,
  "init_expires_at": 1792300000,
  "entries": [
    {"kind": "board", "theme": "quota", "ver": 12, "duration_s": 20, "order": 0},
    {"kind": "photo", "sha256": "3f2a…", "size": 198432,
     "duration_s": 8, "order": 1, "url": "/api/device/photo/3f2a…"},
    {"kind": "photo", "sha256": "9c01…", "size": 241760,
     "duration_s": 8, "order": 2, "url": "/api/device/photo/9c01…"}
  ]
}
```

- **服务端返回完整清单**；设备按自身 `cap/ready` 过滤 `photo` 条目。
  `plv` 是用户级、全局有效。设备从 `ready=false` 变 `true` 时会主动重拉一次清单，
  不依赖 `plv` 变化。
- `entries` 是**完整的期望状态**，数组顺序权威；`order` 从 0 连续到 N-1，作为
  一致性校验/排序键。不认识的 `kind` 整条忽略。
- `kind: "board"`：`theme` 指向 flash 里的主题，`ver` 是该主题帧包版本提示；
  设备仍用现有 `/api/device/frame?theme=` 取最新包，帧更新仍走现有 frame 通知。
- `kind: "photo"`：`sha256` 64 位小写十六进制，`size` 与实际字节一致，
  `url` 是**相对路径**（设备用运行期 API base 拼接）。
- `duration_s` 停留秒数，5–600。
- 初始化授权三字段只用这一套名字：`init_token`（字符串）、
  `init_expires_at`（unix 秒，绝对到期时间，与 `POST /api/photo/init` 返回的
  `expires_at` 同值）、`init_force`（布尔，仅 `--force` 时为 true）。
  三个字段**只在授权有效期内同时出现**；过期、被设备用掉（`init_done`）或撤销后
  整组消失。没有 `init_token` 或没有 `init_expires_at` 时设备绝不格式化。
- `init_expires_at` 由服务端按自己的时钟生成；设备用 SNTP 同步后的时间比较。
  两边时钟差可忽略，但设备时间没对上 SNTP 时必须拒绝格式化。
- 设备格式化成功后把 token 前 8 位写进 `status.photo.init_done`，服务端立即清除
  授权并推进 `plv`；超时也清除。
- 上限：1 个 board + 200 张照片；整份响应控制在 **64KB** 以内（约 25–30KB），
  设备流式解析。响应带 `Content-Length`（设备也能读 chunked，但服务端固定提供）。

### 5.3 增删改全靠「完整状态」语义

**不需要删除指令。** 规则一条：

> 清单是完整的期望状态。设备把索引区里不在清单里的照片项回收（置 `free`）。

改顺序、改时长 → 只改清单，不动文件。删照片 → 它从清单消失，设备下次 GC 掉。
加照片 → 它出现在清单里，设备发现本地没有就下载。

**回收只在本方案的索引/数据区内做**，不碰区外任何扇区——卡上可能有
别的东西，删错一次就再也不会有人信这个产品。

### 5.4 设备能力上报

设备**每次心跳**都带这个字段（含 `state`），服务端按 dev 持久化，并显示在
`stickboxd device show`：

```json
{"photo": {
  "cap": true, "ready": true, "plv": 7, "have": 12,
  "bad": ["a1b2c3d4"], "free_kb": 1234, "state": "ok",
  "init_done": "3f2a9c01"
}}
```

- `cap`：编译期有 SD 驱动；`ready`：卡已初始化且可用；`state`：
  `ok | uninit | fault | absent`。
- `bad`：最多 8 项，每项是 sha256 前 8 位十六进制；整条 status 消息 ≤512B。
- `init_done`：本次格式化用掉的 `init_token` 前 8 位；服务端看到后立即清除授权，
  同一 token 不能再次使用。
- `cap=false` 或字段缺失 = 只显示看板（老固件/无卡设备）。
- 服务端**不按设备过滤清单**（完整清单由设备过滤），这些字段用于诊断、
  `device show`、以及未来排障；服务端不需要为每台设备单独生成版本号。
- 固件心跳缓冲从 256B 扩到 ≥640B，保证整条 ≤512B。

## 6. 资产下载

`GET /api/device/photo/{sha256}`（设备令牌，**必须支持 `Range`**）。

HTTP 侧约定（服务端无状态，不保存续传会话）：

- 首次下载不带 `Range`；重试用**单段** `Range: bytes=n-` 或 `bytes=n-m`。
- 200/206 都带 `Content-Length`；206 带 `Content-Range: bytes n-m/total`。
- 非法/多段/越界 Range → **416** + `Content-Range: bytes */total`。
- `ETag: "<sha256>"`；`Accept-Ranges: bytes`；忽略 `If-Range`。
- `sha256` 一律 64 位小写十六进制；只允许设备取自己主人的照片。

落地流程照 flash 槽那套（先写、后校验、最后才生效）：

1. 索引里已有该 sha256 且状态 `valid` → 跳过
2. 分配一段数据区，续传位置存在**易失 RAM** 中（掉电后从头再下，不信任半写数据）；
   带 `Range: bytes=n-` 续传仅限同一次开机内的重试
3. 边下边写数据区，边算 sha256
4. 下完比对 sha256：**不符 → 释放这段，标记失败**
5. 符合 → 最后写索引项（CRC + `valid`）。**索引项是提交点，所以没有 `valid` 的数据永远不会被播放**

下载串行、低优先级：**取看板帧包的优先级永远高于下照片**。照片晚几分钟到无所谓，
看板迟了就是屏幕上的旧数据。

**校验策略**：下载时全量校验一次，之后不再逐帧校验（200 张 × 250KB 每次开机全量
SHA 太贵）。开机只校验索引项 CRC 与大小；只有在推流时读取出错或解码失败，才对那一张
重新全量校验。

## 7. 失败处理

| 情况 | 行为 |
|---|---|
| 某张 sha256 不符 | 释放未提交的数据区，重试（退避 1/5/30 分钟），连续 3 次失败后**标记跳过** |
| 某张标记跳过 | **轮播继续，跳过这一张。** 一张坏图绝不能让整个轮播停下 |
| 卡满 | 按清单顺序优先保证前面的；装不下的标记跳过。报给服务端 |
| 读取出错 | 重新校验那一张；不符就当「不符」处理 |
| 清单取不到 | 按索引项里已有的 `duration_s`/`order` 继续播。**断网不影响已缓存的内容** |
| 一张都没有 | 退回纯看板（第 8 节） |

失败要让服务端知道（否则用户看不出为什么少了一张）。搭现有的 `status`
上报，不新开通道；字段和大小见 5.4（`state`、`have`、`bad` 前缀、`free_kb`）。

## 8. 没插卡时的行为

**必须和现在完全一样。** 挂载失败 / 没有卡 / 超级块不合法（未初始化）：

- 不挂 SD，不付裸扇区驱动的堆代价
- 清单里的 `photo` 条目**整条忽略**，只播 `board` 条目
- 看板照常显示，取帧、拼接、推流全部不变

这一条成立有个前提，而它已经满足了：T24 保证**主主题即使没有数据也会出帧**
（`rebuildTheme` 的 `primary` 分支）。所以清单里永远至少有一个可播的 `board` 条目。

## 9. 服务端 API 与限制

### 9.1 接口

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| POST | `/api/photo?show=1&secs=8` | agent | 上传原图。`show=1`（默认）成功后自动追加到清单末尾并递增 `plv`；`show=0` 只上传 |
| POST | `/api/photo/init` | agent | 生成一次性初始化 token（默认 10 分钟）；`{"force":true}` 允许格式化 CRC 损坏的卡 |
| GET | `/api/agent/photos` | agent | 列出本用户照片（sha256、字节、上传时间、是否在清单里、`duration_s`） |
| DELETE | `/api/photo/{sha256}` | agent | 删除；同时从清单移除并递增 `plv` |
| PUT | `/api/playlist` | agent | 完整期望状态：重排、改时长、增删条目（含 board 位置） |
| GET | `/api/device/playlist` | device | 清单文档，`ETag: "<plv>"` + `If-None-Match` |
| GET | `/api/device/photo/{sha256}` | device | 照片字节，单段 `Range`，`ETag: "<sha256>"` |

鉴权照 `POST /api/data` 那套：agent 令牌写、设备令牌只读、按 `userID` 归属，
设备只能取自己主人的东西。所有 JSON 响应带 `Content-Length`。

**错误码**（新增接口统一）：
- 400 参数/清单非法；401 令牌无效；403 设备未配对或不属于该用户；
- 404 照片/主题不存在；409 配额满（张数或字节）；413 上传超过 20MiB；
- 415 不支持的图片格式（含 HEIC）；422 无法压到 250KB；416 Range 不合法。

### 9.2 接口细节

**`POST /api/photo?show=1&secs=8`**（agent）
- 请求体是**原始图片字节**（不是 multipart），`Content-Type: image/jpeg|image/png`，
  `Content-Length` 必填，≤20MiB。
- `show` 默认 1：成功后把照片追加到清单末尾（`duration_s=secs`，默认 8，范围 5–600），
  `plv` 递增并通知设备。`show=0` 只入库。
- 成功 `201`：
  ```json
  {"sha256":"<64 lowercase>","size":198432,"width":1920,"height":1080,
   "plv":8,"in_playlist":true}
  ```
  已存在同一 sha256 时返回 `200` 和同样的结构（不重复占配额；仍按 `show` 决定是否追加）。
- 错误：400 无 Content-Length/解码失败；413 超 20MiB；415 格式不支持（含 HEIC）；
  422 压不到 250KB；409 配额满。

**`POST /api/photo/init`**（agent）
- 请求体 `{"force":false}`（可省略）。生成随机 `init_token`，10 分钟有效；
  `force=true` 时设备也允许格式化「魔数存在但 CRC 都坏」的卡。
- 成功 `200`：`{"init_token":"...","force":false,"expires_at":<unix>}`。
- 再次调用会替换旧 token；设备用 `init_done` 上报后立即失效；
  超时后清单不再带 token。

**`GET /api/agent/photos`**（agent）
- `{"photos":[{"sha256","size","width","height","uploaded_at",
  "in_playlist":true,"duration_s":8}]}`，按上传时间倒序。

**`DELETE /api/photo/{sha256}`**（agent）
- 删除照片并从清单移除，`plv` 递增、通知设备。成功 `200 {"ok":1}`；
  不属于本用户或不存在 `404`。幂等删除按 404 处理。

**`PUT /api/playlist`**（agent）
- 完整期望状态：
  ```json
  {"entries":[
    {"kind":"board","theme":"quota","duration_s":20},
    {"kind":"photo","sha256":"<64 lowercase>","duration_s":8}
  ]}
  ```
  `order` 由数组顺序决定，服务端写清单时补 0..N-1；不接受客户端传的 order。
- 校验：1–201 项；至少一个 `board`；`secs` 5–600；theme 必须存在；photo 必须属于
  本用户；sha256 不重复；未知 kind 400。
- 成功 `200`：`{"plv":N,"entries":[...]}`（返回补好 order/url 的版本）。
- 该接口不改变照片库，只改清单；`plv` 递增并通知设备。

**`GET /api/device/playlist` / `GET /api/device/photo/{sha256}`**：见 5.2、第 6 节。

### 9.3 agent 命令

```sh
stickbox-agent photo add [--no-show] <file...>   # 上传；默认自动上屏（show=1）
stickbox-agent photo ls                          # sha 前缀、大小、时长、是否在清单
stickbox-agent photo rm <sha256|前缀>            # 删除（前缀需唯一）
stickbox-agent photo init [--force]              # 生成一次性初始化授权（10 分钟）
```

- `add` 在 macOS 上先尝试用 `sips` 把 HEIC 转成 JPEG、并尝试 `sips -m` 预转 sRGB；
  没有 `sips` 或转换失败时提示用户先转格式。服务端仍做缩放/方向校正/剥元数据。
- `rm` 接受完整 sha256 或唯一前缀，agent 先 `GET /api/agent/photos` 解析再 DELETE。
- `init` 只生成一次性授权；`init --force` 执行前必须二次确认，提示
  “会清空 SD 卡内所有数据”，确认后才调服务端。

### 9.4 服务端必须做的处理

**缩放到 1920×1080 是必须的，不是优化**：

- `probe/dlna-tv/tools/live_ts.py` 实测这台三星 **MJPEG 只到 1080p**，4K MJPEG
  报「格式不支持」
- 手机原图 3–5MB，缩完约 250KB，一次性传输省一个数量级
- 单一流要求所有帧同尺寸——AVI 头里的分辨率是固定的

**处理顺序**：解码（JPEG/PNG，HEIC 415）→ 应用 EXIF Orientation → 等比缩进
1920×1080，比例不符**留白不裁切**（纯黑 `#000000`）→ baseline JPEG 4:2:0，
质量自适应到 ≤250KB（最低 q40，仍超则 422）→ **剥掉 EXIF/GPS/XMP/ICC 等全部
元数据** → 对最终字节算 sha256。

- v1 不做色彩管理：广色域（Display P3）照片剥掉 ICC 后可能略偏淡，文档写明。
  macOS 上 agent 可以尝试 `sips -m` 预转 sRGB；失败就按原样上传。
- **不需要 restart marker**（照片不拼接，DRI 是帧包才需要的东西）。
- 解码前限制像素数（防解压炸弹）与动画图（GIF/APNG 之类直接 415）。

### 9.5 限制

| 项 | 值 | 理由 |
|---|---|---|
| 单张上传 | ≤20MiB | 手机原图够用 |
| 服务端保存 | 只存缩放/剥元数据后的那一份（≤250KB） | 原图不留：省存储，也省内容责任 |
| 每用户张数 | 200，同时总字节 ≤64MiB | 一张 1GB 卡的 5% |
| 淘汰 | **硬配额**：超了拒绝上传（409），不 LRU 淘汰照片 | 删用户照片必须是显式动作 |
| 去重 | 同一最终 sha256 不重复存储；重复上传返回已存在记录 | 内容寻址 |
| LRU | 只允许清理不在任何清单里的临时/孤儿文件 | 不影响用户资产 |

> 如果开「租用公共实例」那档并存用户照片，涉及内容责任（存储生命周期、
> 版权、国内备案），见 `CHANNEL.md` 第 9 节。自建不涉及。

## 10. 固件改动清单

按「尽量不碰带缓冲和 stream.c」的要求排。**前四项都不碰 `stream.c`。**

| # | 改动 | 碰 stream.c？ | 碰带缓冲？ |
|---|---|---|---|
| 1 | SD 挂载/卸载，按需挂载，没卡就安静退回 | 否 | 否 |
| 2 | 裸扇区布局（超级块 A/B、索引区、数据区）的读写与回收 | 否 | 否 |
| 3 | 清单文档的取回与解析（复用 `framefetch.c` 的 HTTPS 流式写法与零分配 JSON 解析思路） | 否 | 否 |
| 4 | 资产下载器：同次开机 Range 续传、sha256、以索引项为提交点、退避重试 | 否 | 否 |
| 4b | `status` 里上报 `photo` 能力与状态（5.4）；无 SD 槽的构建里整块编译掉 | 否 | 否 |
| 5 | **发送循环加第四种模式**：在现有临界区里多快照一个「当前照片」，照片路径走 `read(4KB)→send_all` 到 EOF | **是，加法** | **否** |
| 6 | 每条目的停留计时与推进 | 是，小 | 否 |

第 5 项（照片纯显示，D10）是唯一碰 `stream.c` 的地方，而它是在已有的三模式分支上加第四个分支，
不改任何现有分支的逻辑。`fp_seg_t`、`s_band`、`s_busy`、`s_fp_hold`、
`fp_wait_idle` 全部不涉及。

**不在这个清单里的**：多帧包驻留、槽位按主题寻址、`stream.c` 切 index+base。
那些是看板多主题轮播要的（我之前列的「第三刀」），**照片用不上**——照片在 SD 上，
不占 flash 槽。

## 11. 设备侧实验结论（2026-10-18 已回填）

详见 `experiments/sd-bare-sector-round1.md`：

- 接口：SDMMC 4-bit，引脚与 USB OTG/LCD/按键无冲突。
- 读速：8KB 块单次约 8.3MB/s；持续 2fps 约 480KB/s，失败 0；4KB 块也够用。
- 电视：AVI 从 SD 分块推真实电视，PLAYING 连续 3 分钟不断，画面正常。
- 内存：**互斥设计**（联网取清单/下载 → 写卡 → 卸载 → 本地读卡推流）下可用；
  下载/挂载与取帧 TLS **不并发**，取帧按队列优先级排在下照片之前。
  4KB 缓冲是正式值。
- 掉电：真实拔电可能让卡对板子不可用；卡级损坏只上报 `state=fault`，绝不自动格式化。

### 一个可能省 4 倍 SD 读取的问题（给 USB-TV）

照片是**静止**的，不需要 2fps。T17 定的 2fps 是看板那条路的推荐值，更低的帧率
没测过。**如果 1fps 甚至 0.5fps 电视也能稳住，照片模式下 SD 读取直接降 2–4 倍**。
这是电视行为问题，要上电视测，归 USB-TV 调度。
