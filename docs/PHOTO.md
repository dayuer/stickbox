# 照片上电视：SD 卡本地轮播

状态：**设计稿。** 产品决定已定（`DECISIONS.md` D8–D10）；设备侧细节（第 3、4、11 节）
仍等 esp 的 SD 可行性实验（堆、读速、引脚），结果出来前不作数。
分支 `task/T32-photo-sd`，不合并。本文不依赖 `play`（外部 TS 流）任务。

## 已定决策（用户）

- **D3/D4** 流的起点在设备侧；流内无缝切换，不接受电视黑一下
- **D8** 照片存 SD 卡，**可选功能**：有 SD 槽的板子才有照片，其余板子只显示看板
- **D9** SD 用**裸扇区**，不用 FAT；按需挂载
- **D10** 照片**纯显示**，不叠时钟和用量卡片

## 0. 选型结论（原先的先决冲突，已关闭）

目标板（通用 WROOM-1 / DevKitC-1 / StickBox PCB）多数没有 microSD 槽，所以照片是
**带 SD 槽板子的可选功能**（D8）。后果写死在设计里：

- 无 SD 槽 / 没插卡 / 挂载失败：行为与现在完全一致，见第 8 节
- 服务端**不得**假设每台设备都有照片能力：设备要在 `status` 里上报是否支持（第 5.4 节），
  服务端据此决定要不要给它排 `photo` 条目
- 是否给 StickBox PCB 加 SD 槽是**硬件另议**，不阻塞本设计

## 1. 为什么 SD 是对的原语（如果硬件给得起）

照片的字节**永不变**。流式的本质是「每次播放把同一批字节重发一遍」，
所以对照片用流式等于把同一批字节一遍遍过公网。缓存才是对的原语：
**传一次，播无限次**（`CHANNEL.md` 第 4 节）。

| | 每设备 |
|---|---|
| 200 张 1080p 照片（约 250KB/张） | **50MB 一次性** |
| 同样内容做成 24/7 轮播流 | 约 52GB/月，永远每月 |

**容量不是问题，一张 1GB 卡就够**。256GB 对照片过剩约 1000 倍——那个容量是给视频的。

---

## 2. 设备侧为什么是加法而不是改造

`rom/main/stream.c` 的发送循环已经是为「帧边界切换」设计的。它自己的注释：

> 每帧只在这一个临界区里看一次共享状态，拿到的东西全部快照进局部变量…
> 换帧包、换时钟带、从配对页切到真实看板，都只改共享状态，而共享状态
> 只在帧与帧的边界被读到。

已经有三种模式在帧边界切（帧包 / 时钟带页 / 配对页）。**SD 照片是第四种**，
照同一个模式加：在同一个临界区里多快照一个「当前照片」，往下不回头。

两个关键后果：

- **照片不进带缓冲。** 带缓冲只在有数字卡片要替换时才用。照片是一整张 JPEG，
  没有槽、没有拼接，`s_band` / `BAND_CAP` 一个字节都不碰
- **照片不建段表。** 不用 `fp_seg_t`，直接 `read(8KB) → send_all` 循环到 EOF。
  `s_fp_hold` / `fp_wait_idle` 那条 mmap 生命周期保护也完全不涉及

AVI 的 `00dc` 块头要先写帧长再写字节——照片长度从清单（或文件大小）拿，没问题。

## 3. 存储层：裸扇区（D9）

不用 FAT。理由：设备自己从服务端下载照片，**卡不需要被电脑读**，所以不付 FATFS 的
堆（估 15–25KB，对「取帧最低 40KB」是大头）；掉电语义也可以自己定，照 flash 槽那套
（魔数 + CRC，头部最后写）。

代价（产品上要接受，也要对用户说清楚）：
- **不能插卡直接拷照片**，照片只能经服务端下发
- **首次使用会占用整张卡**：卡上原有 FAT 数据会被覆盖。必须有显式确认
  （例如配对页/App 上"初始化 SD 卡会清空其中内容"），**设备绝不在未确认时写卡**。
  识别方式：超级块魔数不符 → 视为"未初始化"，只上报状态，不写

**堆**：只留 sdmmc 驱动 + 一个 512B 扇区缓冲 + 索引常驻（≤256 项 × 64B = 16KB 若全读；
实际按需读单项，不常驻）。**按需挂载**：清单里没有 `photo` 条目时不初始化 SD。
具体数字等 esp 实测。

## 4. 卡上布局（裸扇区）

512B 扇区。照片是不可变素材，所以布局很简单，不需要通用文件系统。

```
扇区 0、1   超级块 A/B：魔数 "SBPH" + 版本 + 序号 + 索引区/数据区起点 + CRC32
            每次改写交替写 A/B，取序号最大且 CRC 合法的那份（掉电安全）
索引区      固定 256 项 × 64B：sha256(32) | size(4) | 起始扇区(4) | 状态(1) | 保留 | CRC32(4)
数据区      照片本体，按 4KB 对齐，连续存放
```

- **内容寻址**：以 sha256 为键。重复上传不占第二份；改顺序、改时长、改名一个字节都
  不用重传（那些是清单属性）；校验内生
- **项目上限 256**，总用量只占数据区一小段（200 张 ≈ 50MB），**其余容量不用**
- **写入顺序保证掉电安全**：先写数据 → 校验 sha256 → 最后才写索引项的 CRC 与状态为
  `valid`。索引项不完整（CRC 不符/状态非 valid）一律视为不存在
- **分配**：对 ≤256 个索引项按起始扇区排序后 first-fit，**不建位图**（千兆卡位图要 32KB）
- **回收**：清单里没有的 `valid` 项置为 `free`。**回收只在本命名空间（上述索引/数据区）内，
  不触碰区外任何扇区**

顺序和显示时长不在卡上，在清单里。

## 5. 播放清单协议

### 5.1 MQTT 只报版本，清单走 HTTPS

现状（T24 已上线）：`printer/{dev}/frame` 发 `{"ver":N,"pl":[{id,ver,secs}]}`。

**照片库不能走内联 `pl`**：200 张照片的元数据内联进 MQTT 是几十 KB 的消息，
而 MQTT 消息该保持很小。改成和帧包一样的两段式——**通知版本，设备去取**：

```json
{"ver": 12, "plv": 7}
```

- `ver` 保持原义（主主题帧包版本），**老固件只认它，行为不变**
- `plv` 是播放清单版本。设备发现 `plv` 变了 → `GET /api/device/playlist`
- 内联 `pl` 仍受 T24 修复的硬预算约束（最多 8 项、整条消息 ≤800 字节，老固件 MQTT
  缓冲只有 1024 字节，超出整条丢弃且之后不再更新）。`plv` 字段只增加几个字节，不得
  突破该预算；**清单文档是唯一权威**，内联 `pl` 只作兼容

### 5.2 清单文档

`GET /api/device/playlist`（设备令牌，带 `ETag` / `If-None-Match`）：

```json
{
  "plv": 7,
  "entries": [
    {"kind": "board", "theme": "quota", "secs": 20},
    {"kind": "photo", "sha256": "3f2a…", "size": 198432, "secs": 8},
    {"kind": "photo", "sha256": "9c01…", "size": 241760, "secs": 8}
  ]
}
```

- `entries` 是**完整的期望状态**，按播放顺序排
- `kind: "board"` 指向 flash 里的帧包（照旧），`kind: "photo"` 指向 SD 上的文件
- `secs` 是停留秒数，5–600（和 `theme.MinDwell`/`MaxDwell` 一致）

### 5.3 增删改全靠「完整状态」语义

**不需要删除指令。** 规则一条：

> 清单是完整的期望状态。设备把索引区里不在清单里的照片项回收（置 `free`）。

改顺序、改时长 → 只改清单，不动文件。删照片 → 它从清单消失，设备下次 GC 掉。
加照片 → 它出现在清单里，设备发现本地没有就下载。

**回收只在本方案的索引/数据区内做**，不碰区外任何扇区——卡上可能有
别的东西，删错一次就再也不会有人信这个产品。

---

### 5.4 设备能力上报

设备在 `status` 里带一个很小的字段，服务端据此决定要不要给它排 `photo` 条目
（没 SD 槽的设备永远收不到 `photo`，也就不会白下载）：

```json
{"photo": {"cap": true, "ready": true, "plv": 7, "have": 198, "bad": ["3f2a…"], "free_kb": 1048576}}
```

`cap`：板子有 SD 驱动；`ready`：卡已初始化且可用。`cap=false` 或字段缺失 = 只显示看板。

## 6. 资产下载

`GET /api/device/photo/{sha256}`（设备令牌，**必须支持 `Range`**）。

落地流程照 flash 槽那套（先写、后校验、最后才生效）：

1. 索引里已有该 sha256 且状态 `valid` → 跳过
2. 分配一段数据区，续传位置存在**易失 RAM** 中（掉电后从头再下，不信任半写数据）；
   带 `Range: bytes=n-` 续传仅限同一次开机内的重试
3. 边下边写数据区，边算 sha256
4. 下完比对 sha256：**不符 → 释放这段，标记失败**
5. 符合 → 最后写索引项（CRC + `valid`）。**索引项是提交点，所以没有 `valid` 的数据永远不会被播放**

下载串行、低优先级：**取看板帧包的优先级永远高于下照片**。照片晚几分钟到无所谓，
看板迟了就是屏幕上的旧数据。

**校验策略**：下载时全量校验一次，之后不再逐帧校验（200 张 × 250KB 每次开机全量
SHA 太贵）。开机只校验索引项 CRC 与大小；只有在推流时读取出错或解码失败，才对那一张
重新全量校验。

## 7. 失败处理

| 情况 | 行为 |
|---|---|
| 某张 sha256 不符 | 删 `.part`，重试（退避 1/5/30 分钟），连续 3 次失败后**标记跳过** |
| 某张标记跳过 | **轮播继续，跳过这一张。** 一张坏图绝不能让整个轮播停下 |
| 卡满 | 按清单顺序优先保证前面的；装不下的标记跳过。报给服务端 |
| 读取出错 | 重新校验那一张；不符就当「不符」处理 |
| 清单取不到 | 沿用 SD 上的 `manifest.json` 副本继续播。**断网不影响已缓存的内容** |
| 一张都没有 | 退回纯看板（第 8 节） |

失败要让服务端知道（否则用户看不出为什么少了一张）。建议**搭现有的
`status` 上报**，加一个很小的字段，不新开通道：

```json
{"photo": {"plv": 7, "have": 198, "bad": ["3f2a…"], "free_kb": 1048576}}
```

## 8. 没插卡时的行为

**必须和现在完全一样。** 挂载失败 / 没有卡 / 超级块不合法（未初始化）：

- 不挂 SD，不付裸扇区驱动的堆代价
- 清单里的 `photo` 条目**整条忽略**，只播 `board` 条目
- 看板照常显示，取帧、拼接、推流全部不变

这一条成立有个前提，而它已经满足了：T24 保证**主主题即使没有数据也会出帧**
（`rebuildTheme` 的 `primary` 分支）。所以清单里永远至少有一个可播的 `board` 条目。

## 9. 服务端 API 与限制

### 9.1 接口

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| POST | `/api/photo` | agent | 上传原图，返回 `sha256` 与缩放后大小 |
| GET | `/api/agent/photos` | agent | 列出本用户照片（sha256、字节、上传时间、是否在清单里） |
| DELETE | `/api/photo/{sha256}` | agent | 删除；同时从清单移除 |
| PUT | `/api/playlist` | agent | 设置顺序与每张时长（含看板条目的位置） |
| GET | `/api/device/playlist` | device | 清单文档，带 ETag |
| GET | `/api/device/photo/{sha256}` | device | 照片字节，**必须支持 Range** |

鉴权照 `POST /api/data` 那套：agent 令牌写、设备令牌只读、按 `userID` 归属，
设备只能取自己主人的东西。`internal/auth/acl.go` 的两级准入直接复用。

### 9.2 服务端必须做的处理

**缩放到 1920×1080 是必须的，不是优化**：

- `probe/dlna-tv/tools/live_ts.py` 实测这台三星 **MJPEG 只到 1080p**，4K MJPEG
  报「格式不支持」
- 手机原图 3–5MB，缩完约 250KB，一次性传输省一个数量级
- 单一流要求所有帧同尺寸——AVI 头里的分辨率是固定的

**比例不符的照片做留白，不裁切。** 4:3 的照片放进 16:9 要么留黑边要么裁掉两侧；
裁切会切到人脸，这是用户自己的照片，不能替他裁。留白用看板的底色 `#1D2D3D`。

编码：baseline JPEG、4:2:0、**不需要 restart marker**（照片不拼接，DRI 是帧包
才需要的东西），自适应质量压到 ≤250KB。

### 9.3 限制（建议值，待定）

| 项 | 建议 | 理由 |
|---|---|---|
| 单张上传 | ≤20MB | 手机原图够用 |
| 服务端保存 | 只存缩放后的那一份（约 250KB） | 原图不留：省存储，也省内容责任 |
| 每用户张数 | 200（约 50MB） | 一张 1GB 卡的 5% |
| 淘汰 | 每用户配额，超了拒绝上传而不是静默删 | 删用户照片必须是显式动作 |

> 如果开「租用公共实例」那档并存用户照片，涉及内容责任（存储生命周期、
> 版权、国内备案），见 `CHANNEL.md` 第 9 节。自建不涉及。

## 10. 固件改动清单

按「尽量不碰带缓冲和 stream.c」的要求排。**前四项都不碰 `stream.c`。**

| # | 改动 | 碰 stream.c？ | 碰带缓冲？ |
|---|---|---|---|
| 1 | SD 挂载/卸载，按需挂载，没卡就安静退回 | 否 | 否 |
| 2 | 裸扇区布局（超级块 A/B、索引区、数据区）的读写与回收 | 否 | 否 |
| 3 | 清单文档的取回与解析（复用 `framefetch.c` 的 HTTPS 流式写法与零分配 JSON 解析思路） | 否 | 否 |
| 4 | 资产下载器：同次开机 Range 续传、sha256、以索引项为提交点、退避重试 | 否 | 否 |
| 4b | `status` 里上报 `photo` 能力与状态（5.4）；无 SD 槽的构建里整块编译掉 | 否 | 否 |
| 5 | **发送循环加第四种模式**：在现有临界区里多快照一个「当前照片」，照片路径走 `read(8KB)→send_all` 到 EOF | **是，加法** | **否** |
| 6 | 每条目的停留计时与推进 | 是，小 | 否 |

第 5 项（照片纯显示，D10）是唯一碰 `stream.c` 的地方，而它是在已有的三模式分支上加第四个分支，
不改任何现有分支的逻辑。`fp_seg_t`、`s_band`、`s_busy`、`s_fp_hold`、
`fp_wait_idle` 全部不涉及。

**不在这个清单里的**：多帧包驻留、槽位按主题寻址、`stream.c` 切 index+base。
那些是看板多主题轮播要的（我之前列的「第三刀」），**照片用不上**——照片在 SD 上，
不占 flash 槽。

## 11. 要 esp 先验的（结果出来前本文第 3、4 节的细节都不作数）

1. **引脚**：SDMMC 1-bit / 4-bit 还是 SPI；和现有用脚（0/12/13/14/15/16/17/18/21）
   是否冲突
2. **堆**：裸扇区方案的常驻与峰值占用（刚挂载 / 读取中 / 与取帧 TLS 并发三个时刻的
   最低空闲堆）。对「取帧最低 40KB」是生死线。FAT 已否决，不用测
3. **读速**：能否稳定 500KB/s 以上。注意这是**持续**读——见下一条
4. **持续读的量**：2fps 下一张照片在它的停留期内会被反复读。停留 8 秒 = 16 次
   读同一张 250KB = **4MB**。所以稳态是约 500KB/s 不间断，24/7
5. **8–13KB 分块把 SD 上的 JPEG 直接推给电视**能否跑通，帧节奏是否稳

### 一个可能省 4 倍 SD 读取的问题（给 USB-TV）

照片是**静止**的，不需要 2fps。T17 定的 2fps 是看板那条路的推荐值，更低的帧率
没测过。**如果 1fps 甚至 0.5fps 电视也能稳住，照片模式下 SD 读取直接降 2–4 倍**，
第 3/4 项的压力大幅缓解。这是电视行为问题，要上电视测，归 USB-TV 调度。

## 12. 开放问题

已关闭（用户决定）：板子选型 → D8 可选功能；FAT 还是裸扇区 → D9 裸扇区；
照片是否叠时钟 → D10 纯显示。

仍开放：
1. **照片模式的帧率** —— USB-TV 用 `tvcheck -fps 1` / `0.5` 在电视上测，结果回填第 11 节
2. 看板与照片的默认编排：先看板后照片轮一圈？看板占多少比例？—— 产品
3. 首次使用"初始化 SD 卡会清空内容"的确认入口放哪（配对页 / agent 命令）—— 产品 + esp
4. StickBox PCB 是否加 SD 槽 —— 硬件，不阻塞本设计
