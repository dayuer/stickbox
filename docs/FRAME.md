# 帧接口约定（T13a ↔ T13b）

状态：**方案 D 已选定**（T13b 确认设备可做）。还剩两件事：
USB-TV 找用户确认时钟卡片几何偏离；T13b 上板验证三星电视能解码拼接流。

本文约定服务端（T13a）交给设备（T13b）的**底帧 + 字形图集 + 索引**，
以及设备每分钟按 HH:MM 拼接时的字节级规则。

方案 A（整带掩码）和 B（小时间条）已放弃：A 损失抗锯齿且颜色被状态绑死，
B 丢翻页钟外观。D 只换成块的 MCU 字节，不动 DCT，画面保持全彩。

---

## 1. 为什么是 D

设备不需要任何重编码：

- 底帧和字形图集都用 **DRI=8** 编码，每 8 个 MCU（恰好一张卡片宽）
  一个 restart 区间，字节对齐、DC 预测清零。
- 四张数字卡片都落在 8 MCU 边界上，所以每张卡片每行正好是一个完整
  restart 区间，可以直接按字节替换。
- 替换段和被替换段的 interval 数相同，后续 MCU 的 RSTn 序号不变；
  每段末尾的 RSTn 按目标 interval 序号补一个字节即可。
- 推流侧把 `stream.c` 的三段拼接扩成逐行多段；**只缓冲每行的卡片区**
  （12 行最坏 13,089B，上界 14,626B；单块 `BAND_CAP` 16KB；`s_band` 是双缓冲，
  两块共 32KB）。
  整条时钟带 29–32KB，双缓冲要 64KB，会吃掉 T8 之后的全部余量，**不可用**。

`rom/main/jband.h` 的 `jb_encode_rows` 在 D 里**不使用**；保留作背景参考。
设备只需要两个能力：mmap 读底帧、memcpy 拼时钟带。

### DRI=8 的实测代价

同一张底帧（1920×1080，q=82）：

| DRI | 帧大小 |
|---|---|
| 8 | 181,250 B |
| 120（每行） | 176,977 B |
| 不设 restart | 176,504 B |

DRI=8 只多 **4.7KB（+2.7%）**，远低于先前 20–35KB 的估计。

## 2. 版面（D 方案的时钟）

为了让四张卡片都落在 8 MCU 边界上，时钟几何相对设计稿有调整：

| 项 | 设计稿 | D 方案 |
|---|---|---|
| 卡片 | 132×184 | **128×192**（8×12 MCU），内容宽 122 + 右侧 6px 黑缝 |
| 卡片 x | 1241 / 1379 / 1559 / 1697 | **1152 / 1280 / 1536 / 1664** |
| 卡片 y | 67 | **64** |
| 冒号区 | 48px | **128px**（8 MCU），两点居中 |
| 时钟面板 | x 1222, w 626 | **x 1134, w 714**（右缘仍是 1848） |
| 卡片间距 | 6px 面板底 | 6px 黑缝画在图块内部 |

- 卡片起始 MCU 列：72 / 80 / 96 / 104，都是 8 的倍数。
- 时钟带：MCU 行 **4..15**（y 64..256），12 行；每行 15 个 interval。
- 底帧里时钟带以外的部分完全按设计稿渲染（面板、边框、角标、冒号都在）。
- 设备只替换 4×12 = 48 个卡片 interval，其它字节原样保留。
- 铰链保留；卡片左右各 2px 的金属卡扣省略（会伸出图块）。
- 冒号不闪烁；翻页动画不做（帧每分钟一换）。

> ⚠ 卡片从 132×184 变成 128×192、时钟整体左移并加宽，需要 USB-TV
> 找用户确认。这是 D 的唯一可见代价。

## 3. JPEG 编码

底帧与字形图集由 T13a 的 `internal/jpegrestart` 编码：

| 项 | 值 |
|---|---|
| 格式 | baseline、8 位、YCbCr 4:2:0 |
| 尺寸 | 1920×1080 → 120×68 MCU |
| DRI | **8**（每 8 个 MCU 一个 restart 区间） |
| RST | 每个 interval 末尾 `FF D0+n`，n = interval 序号 mod 8 |
| 量化表 | 两张，固定 q=82，底帧与图集必须完全相同 |
| 哈夫曼表 | 标准 4 张（DC/AC 亮度、色度） |
| 最后一帧 | 最后一个 interval 不带 RST（字形图集块例外，见下） |

所有段必须用同一组量化/哈夫曼表，否则解码器会用第一张表的参数解后续段。
服务端把质量固定在 `frame.Quality = 82`，不随数据变化。

## 4. 帧包

三样东西，一起下发、一起写进同一个 **256KB** flash 槽：

1. `base.jpg` — 底帧，卡片区是空白卡片（底 + 铰链 + 黑缝，无数字）
2. `atlas.bin` — 0–9 十块 128×192 图块的 interval 字节，顺序拼接
3. `meta.json` — 索引

### 4.1 meta.json

```json
{
  "v": 1,
  "width": 1920,
  "height": 1080,
  "frame_sha256": "<底帧 SHA-256>",
  "jpeg": { "dri": 8, "mcu_cols": 120, "mcu_rows": 68 },
  "band": {
    "rows": [4, 16],
    "run": { "off": 12345, "len": 32315 },
    "row_runs": [ { "off": 12400, "len": 308 }, ..., 共 12 段 ],
    "max_band_bytes": 13089
  },
  "slots": [
    {
      "x": 1152, "y": 64, "w": 128, "h": 192, "mcu_col": 72,
      "runs": [ { "off": 12400, "len": 68 }, ..., 共 12 段 ]
    },
    { "x": 1280, "mcu_col": 80, "...": "..." },
    { "x": 1536, "mcu_col": 96, "...": "..." },
    { "x": 1664, "mcu_col": 104, "...": "..." }
  ],
  "atlas": {
    "size": 28459,
    "sha256": "<图集 SHA-256>",
    "digits": [
      { "d": 0, "runs": [ { "off": 0, "len": 210 }, ..., 共 12 段 ] },
      ...
      { "d": 9, "runs": [ ... ] }
    ]
  }
}
```

- `band.run.off/len`：底帧 JPEG 里整条时钟带的绝对字节范围。
  起点是第 4 行第 0 个 interval，终点是第 15 行最后一个 interval 末尾
  （含它的 RST）。约 29–32KB。
- `band.row_runs`：12 段，行优先；每段只覆盖该行的时钟列
  **MCU 列 72..112（5 个 interval）**，起点是该行 col 72 的 interval，
  终点是 col 111 的 interval 末尾。12 段合计约 **6.0KB**。设备可以按行
  拼接，不必把整条 32KB 带子读进 RAM。
- `band.max_band_bytes`：服务端遍历 00:00–23:59 全部 1440 个时刻后，
  12 行卡片区替换完的最大字节数（当前 **13,089**，出现在 08:28；
  理论上界 4×最宽数字 3187 + 静态 662 = 13,410）。设备加载帧包时
  必须拿它和 `BAND_CAP` 比较，超了拒绝整包；每次拼接再做一次长度断言。
  服务端也有一道同样的护栏：`frame.BandCap = 16KB`（必须与
  `rom/main/stream.h` 的 `BAND_CAP` 一致），`frame.Build` 发现
  `max_band_bytes` 超限直接返回错误，不让坏帧包出服务端。
- `slots[].runs`：12 段，行优先；每段是底帧里该卡片该行的
  absolute `(off, len)`，正好覆盖一个 8-MCU interval（含 RST）。
- `atlas.digits[].runs`：12 段，相对 `atlas.bin` 起点；每段也是
  8 个 MCU + 结尾 RST。
- `frame_sha256` / `atlas.sha256`：设备写入前校验。

### 4.2 设备拼接

```text
for slot in 0..3:
    d = HHMM[slot]              // 时十位、时个位、分十位、分个位
    for row in 0..11:
        seg = atlas[digits[d].runs[row]]
        interval = (4 + row) * 15 + slots[slot].mcu_col / 8
        seg[len-1] = 0xD0 + (interval % 8)   // 补一个字节的 RSTn 序号
        band[slots[slot].runs[row] - band.run.off] = seg
```

- 48 段替换，每段只改最后 1 字节；无 DCT、无 Huffman 重编。
- 段长度可以变化，所以时钟带的总长度每分钟会变；`stream.c` 的
  band 段用动态长度即可。
- 冒号在底帧的时钟带里，不参与替换。
- 两种缓冲方式（都验证过字节规则）：
  1. **逐行**（唯一可行）：按 `band.row_runs` 取 12 行时钟列，替换 4 个
     数字段。遍历 1440 个时刻的实际最坏 **13,089B**（08:28），保守上界
     14,626B（各槽独立取最长数字段）。`BAND_CAP` 设 **16KB**，双缓冲 32KB。
     推流按「行前连接段 + 行时钟段」发送，约 26 段/帧。
  2. **整带**：`band.run` 29–32KB；双缓冲 64KB，和 MQTT TLS 抢堆，
     T8 最低 63.5KB 的余量会被吃光。只留给主机工具/调试，设备不要用。

## 5. 实测

`go run ./cmd/render-preview`（固定 2026-10-17 12:47）：

| 状态 | 底帧 | 图集 | 元数据 | 合计 | 拼接帧 |
|---|---|---|---|---|---|
| 超速 | 181,250 | 28,459 | 4,965 | 214,674 | 186,113 |
| 安全 | 178,046 | 28,459 | 4,965 | 211,470 | 182,909 |
| 危险 | 184,418 | 28,459 | 4,965 | 217,842 | 189,281 |
| 用满 | 180,102 | 28,459 | 4,965 | 213,526 | 184,965 |
| 无数据 | 146,899 | 28,459 | 4,965 | 180,323 | 151,762 |

最坏 217,842 B，256KB 槽位余约 44KB。时钟带：整带 28,885–32,315 B；
逐行时钟列 12 段合计 **6,030 B**（每行 503B）；替换后实际最坏 **13,089 B**
（08:28），保守上界 14,626 B；`BAND_CAP` 16KB，双缓冲 32KB。

主机侧验证（`internal/frame` 测试）：

- `Splice(12,47)` 与直接渲染整帧逐像素比较，**最大差值 0**（5 种状态）。
- 任意 `00:00 / 09:05 / 12:47 / 23:59` 拼接后，时钟带与直接渲染逐像素一致。
- Go `image/jpeg` 与 Homebrew libjpeg 的 `djpeg` 都能正常解码拼接帧。
- 三星电视实机解码待 T13b 上板验证。

## 6. 偏差清单

1. 卡片 132×184 → 128×192；内容宽 122 + 6px 内嵌黑缝
2. 时钟面板左移加宽（x 1134..1848），卡片组左移
3. 冒号区 48 → 128px，两点仍居中
4. 卡片左右金属卡扣省略
5. 冒号不闪烁、翻页动画不做
6. 其余版面、颜色、字体与设计稿一致（底帧全彩，无 1-bit 化）
